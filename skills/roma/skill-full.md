---
name: roma
description: Keep the user's tasks, notes and lists in their Roma workspace, and pick them up again. Use when the user mentions their tasks, to-dos, reminders, notes, lists, automations or experts, mentions something they need to do, asks what to work on next, what is due or what is on their plate, asks what they wrote down or decided earlier, asks to save, remember or add something for later, asks you to work the way one of their experts does, opens you from Roma to work on one of its items, or works through a plan, a decision, a comparison or a piece of research with you: that work lives in a Roma task. Not for a quick factual question or a one-off rewrite.
---

Roma is the user's own workspace: lists of items, and automations. Their Tasks list and every list shaped for tasks keep a status and a due date on each item; their Notes list keeps prose; any other list keeps what its properties say (a reading list, contacts, expenses). Every tool acts as them, on their own lists and on the items others shared with them (a read marks those `isSharedWithMe` and says what `update_items` admits).

## Start oriented

A conversation about their work, plans or anything they keep starts with one `get_context` call; during a setup the claim comes first (`register_agent` with the kind, the guide's section 3), then `get_context`. It returns who they are, today in their timezone, what they asked Roma to remember, their lists with ids and properties (the Tasks list and the Notes list named), what is due and in progress, recent notes, and their automations. The agent uses the ids it returns and never guesses one. When the user gives the agent one item by id, the agent reads that item and this call is not needed.

## The first time Roma is connected

A first setup, and every time the person sends the sentence from their agent's page in Roma ("From now on I want to use Roma whenever we work on tasks. Set Roma up for me by following the instructions at https://roma.app/agents.md and guide me through the steps."), goes by the guide: https://roma.app/agents.md (Roma guide v1), its start page, then the rules page and the kind page linked from it (ChatGPT: https://roma.app/agents/chatgpt.md). On Roma Staging the person's sentence, every message of the setup and the standing block say "Roma Staging" where this text reads "Roma": the text is served there with the addresses swapped; its standing block names the build, and the rest of the brand stays as written. The agent reads all three and guides the person through the steps one at a time; the page says what the agent says, what it waits for, and what it does itself. Once Roma is connected, the Roma tool `get_guide` returns the start page, the rules and the kind page as text (parts "index", "rules" and "section"; "section" alone when the other two were read already); an agent uses it whenever a page does not open. The setup has two parts, and the agent says so first: part 1, the agent can talk to Roma (connect, who it is), works for everyone; part 2, Roma can reach the agent (the listening of its kind), is what lets the person delegate work to it from Roma; the standing line for the person's own settings is offered last, after the close, as the guide says. ChatGPT: the whole setup lives in one Work chat (its message box reads "Work with ChatGPT"); in a regular chat ChatGPT says so and sends the person to a new Work chat with their sentence, and does nothing else there. A Work chat on chatgpt.com or in the ChatGPT app is ChatGPT, kind "chatgpt", even when its environment calls itself Codex or names its tools codex_apps (9 Nov 2026): it follows the ChatGPT page, the paragraph below is not for it, and no Codex instructions file is written from it. The "Set up Roma" button after installing the plugin opens such a Work chat with the message "Help me set up @Roma with the $roma skill": that message is the person's sentence, so the setup starts with the guide at once. On chatgpt.com that chat is a cloud Work chat and the whole setup runs in it. So a chat without the subscribe tool does part 1 of the guide, the steps its ChatGPT page counts as part 1, then sends the person to https://chatgpt.com/work with the same message, as the ChatGPT help page says. A Dot sets itself up from the same sentence, as its page says. The agent never asks the person for a key or an address the claim's answer gave, and never asks the person to make a test task to check the door: Roma tests it itself. Anything beyond the guide's steps (imports of old tasks, a routine of the agent's own, memories, a second door) the agent offers once and does only when the person says yes. Where the app offers choice cards (a question with numbered options), the agent uses them for every yes/no and every wait for done; otherwise it writes the options as a numbered list and asks for the number.

Everything from Keep things on is for every agent.

Right after connecting, a command-line agent tells Roma who it is: `register_agent` with its kind from the list, and `name`, the name it goes by (no name of its own: it leaves the field out). The claim binds the sign-in to the agent's record, or makes one, so its work lands there and no second record grows from the sign-in. After a reconnect or a new sign-in the agent claims again with its kind and the same name: Roma takes it as the same record connecting again. A name Roma does not know may be refused with a list of the person's agents of that kind: the agent claims again as the refusal says (with that agent's agentId when it is that agent, with asNew true when it is a new one), and the agent asks the person the refusal's quoted question only when it cannot know. Where the answer carries a `keep` line, the agent saves it where only it reads it (its own memory; beside this skill only when no other agent shares the skill) and passes its agentId on later claims too. Claude Code and Codex get no `keep` line and never pass an agentId: kind and name are their whole claim. Then three short lines say how this works from here: the person mentions a to-do in any chat and the agent puts it on Tasks; work the two do together lives in a task the agent keeps current, and the agent suggests the next tasks as they come up; the person asks "what's on my plate" or "where did we land on X" and the agent answers from Roma; their lists are at roma.app and in the Roma app on their phone. The agent asks once whether to keep working this way; when the person's message already carries that rule (a "from now on, keep my to-dos and my work in Roma" line, or the standing block below), that is the yes, and the agent skips the question. On a yes: an agent that can write files (Codex, Claude Code, Gemini CLI, Cursor) appends the standing block below to its global instructions file in the same turn (Codex: ~/.codex/AGENTS.md; Claude Code: ~/.claude/CLAUDE.md; Gemini CLI: ~/.gemini/GEMINI.md) and says in one sentence where it was saved and that a new session reads it; an agent that cannot write a file saves the block to its memory in the same turn, says in one sentence that it was saved, and gives the person the block to keep in the app's standing instructions, because a memory alone does not make the agent reach for Roma in a chat about something else, and the block does. A rule already there that names an older guide version is replaced by this one. The agent asks once, never again. The standing block is the person's own rule, in the person's words, one text with agents.md (on Roma Staging it reads Roma Staging and that build's own agents.md page):

## Keep things

- A to-do is an item on the Tasks list: `create_items` with the list word "tasks", one entry per to-do; several at once (a list the user dictates, the work another agent hands over) are one call. To file it on another list shaped for tasks, that list is named by id. A due date is a day, `dueAt` as `YYYY-MM-DD`, unless they said a time, then `YYYY-MM-DDTHH:MM` in their local time, which also sets a reminder at that moment; "remind me about it tomorrow" on a day is `reminderAt` beside the day, and the reminder rings at their default hour.
- A plan, a reference, meeting notes or a draft is an item on the Notes list: `create_items` with the list word "notes" and the body as Markdown.
- A set of similar things (books, contacts, expenses, wines) is items on the list they keep for it: `list_lists` for the list and its property ids, then `create_items` with values for those properties, many entries in one call. A list they do not have yet is `create_list`.
- Before it creates anything, the agent runs `search` once. What they refer to usually already exists, and a second copy drifts from the first. An addition goes into the existing item with `update_items` edits.

## Pick things up

- "What's on my plate" and "what should I work on next" are `get_context`; a longer or filtered list is `list_items` (the Tasks set by default, or one list by id). The answer comes from Roma, not from the conversation alone.
- "What did I write down about…" is `search`, then `get_item` for the full text.
- A count, a total or a filtered slice of one list ("how many are unread", "expenses in March") is `query_items`.
- "What did my automation find" is `list_automations`, then `get_automation_runs`. The agent starts an automation only when they ask, with `run_automation`; its result lands in their Roma chat.

## Work on one thing

The agent reads the item first: `get_item` returns the item with its body, its values by property name, its list, and, for a meeting recorded into it, the transcript. The body comes back with a short handle in front of every block, a `bodyVersion`, and a line of guidance about this item's state. Then `read_chat_messages`: what the person wrote there since an agent last posted is usually the brief, or the answer the agent was waiting for.

- **The body is the work, written for someone who was not there.** A task's body is its documentation (the shape is under What goes in Roma below); a note whose body is the thing itself, a draft, a plan, a reference, keeps its body as that thing, with nothing added above or below it. The agent never pastes the conversation itself into either. It edits the body in place with `update_items` `edits`: `replace` a block, `insert` next to one (`after`, `before`, `child`, `sectionEnd`, or `start` / `end` of the body), `delete`, `setChecked` a checklist item, `move`, `replaceText` a phrase, or `rewrite` the whole body with the `bodyVersion` that was read. The agent may change any of it, its own text and the person's, the way a collaborator would; version history keeps every change under the agent's name. The agent never adds a second copy of something already there, an "updated" section or a note about a correction: it fixes the block itself. Every body edit goes with a message on the same call: one short line for the person, at most 420 characters, what changed and what is needed from them; without it the edit is refused. What the next agent should know beyond the edit goes in agentDetail beside it, folded away from the person, in a fixed shape: six bold labels in this order, each only when it has content, one line per entry: Did, Decided, Dropped, Facts, Next, Open. Facts are pointers (a pull request, a commit, a path, a command, a link), never pasted output; nothing the body or the message already says.
- **The work continues; it is not redone.** What the body already holds is where the work starts. Work found done is left done, and said so.
- **Good writing.** Concise, clear Markdown: headings from H2 (H3 inside) where they help, bullets where they help, a state as a word, never an emoji. A task's subtasks are a checklist (`- [ ]`), ticked as the work moves. No preamble, no restating the title, no sign-off.
- **Status.** The agent sets a task to `inProgress` (`update_items`) when the work actually starts, not on opening it. It sets `completed` only when the person says it is done, or has told the agent to mark its own work done when it finishes.
- **A delegated task.** When the agent's record sits in a task's Delegate cell, `get_item` says who delegated it and when, and `agentState` says where it stands (working, waitingForYou, done, failed). On long work the agent keeps the body current along the way: an `update_items` call with a short message at least every two hours is the progress line, a bare post is not; after four hours with no write from the agent, Roma releases it. When the work is done, the agent gives the task back: `handoff: "returned"` on the item in the `update_items` call that writes the last result, with the last `message` on that same call. A return without its message is refused. The agent stays in the cell; the task reads Done. An agent that cannot go on asks the person with `needsInput: true` and ends its turn: they are told at once, and a delegated task then reads Waiting for the person and stays with the agent. A delegated task can be given back instead, with a message that says what blocked the agent: a returned task reads Done, so only the message says it is not. A plain message leaves the person thinking the agent is still working. Blocked on the person's answer: the agent posts the one question with `post_chat_message` and `needsInput: true`. Roma then keeps the task with the agent; without it Roma gives the task back when the run ends. A body write that ends on that question carries `needsInput: true` beside its `message` instead. A Reply or a mention from the person on a task the agent already gave back, or on one it never held: the agent just answers; no return is needed (one sent anyway gives nothing back; the rest of the call is written, and the answer's `warning` says so). The agent never clears itself from the cell. A guidance line that says the task was reassigned: the agent does nothing.
- **The thread is for the person.** `post_chat_message` lands a message under the agent's name on the item, which the person sees on every device. A post is for an action taken outside Roma (a mail sent, an event created, a pull request opened) with its link, for the one question the agent is blocked on (with `needsInput: true` on a delegated task), and to answer the person's Reply or mention when nothing in the body changes; a body edit already carries its own message. There is no post per step. An agent never posts a second time to say it is finished. The person decides when a task is done. In doubt, fewer posts.
- **The log is Roma's.** Every change to the item, every post and every body edit with the text it added is written by Roma into the item's log as it happens; nothing writes into it from here. `read_log` shows what changed and why, for an agent about to continue another's work.
- **The summary is Roma's.** Above the body Roma keeps a summary of the item, written from the body and the log after every change. The agent reads it; it never writes it and never copies it into the body.

## What goes in Roma

Roma is the person's task list, and three things land there without being asked. A to-do they mention is a task on Tasks. Work the person and the agent do together on a topic (a plan, a decision, a comparison, a piece of research, a draft they are working toward) lives in that topic's task: the agent makes the task once when the work starts, keeps its body current along the way, sets its status as the work moves, and makes the next to-dos the work produces tasks of their own that name it. And a question about what to work on next is answered from Roma. A note is created only when the person asks for one (a draft, a reference, a plan they want as a document), on Notes. A quick question or everyday chat leaves nothing. An id or a link from the person is the item. A `search` comes before anything is made, and before every item of a bulk run: a second copy drifts from the first. The first write comes as soon as the work starts, then one whenever something changed: a decision, a result, a next step, a new fact. Writing never waits for the end of the conversation; nobody knows when it ends. The agent tells the person in one line which item it created or updated; no question comes first. A write the host refuses: the agent retries it once right away as its own call with a shorter body and without links or quoted text from fetched pages, then adds the sources in a second write; only if the retry is refused too, the agent says so in one line. The agent never drops a write without a line that says so. Roma not connected: the agent says so at the start rather than going on without it.

**A task's body is the work.** The person's brief and checklist stay as they wrote them; the agent adds under them and ticks the checklist as the work moves. Where things stand is Roma's Summary above the body, not a paragraph in it. What goes in the body: the findings, the draft, the numbers, the proof (a pull request, a test run, a link), and a decision as one plain line with its reason where it belongs. Open questions go to the person in the message, not into the body. The next to-dos the work produces are tasks of their own. A section exists only when it has content, and a next step is never invented.

**A note whose body is the thing itself** (a blog draft, a plan, a reference) keeps its body as that thing, with nothing added above or below it; if there is work to track, a task beside it carries the shape above.

**Written for someone who was not there.** Short sentences of about 15 words, one idea each; the main point first; active voice that names who; plain everyday words around the precise technical terms, each term explained once. The meaning sits in the first few words of every heading and bullet. Absolute dates (19 Oct 2026), never "yesterday". Headings start at H2, H3 inside, never deeper; no horizontal lines; bold for at most one phrase; prose for reasons and bullets for three or more parallel things, checklists only for actions. Digits for numbers. No emoji: a state is a word. No em dashes; no "not just X, but Y"; no filler such as "crucial", "robust", "seamless", "it's worth noting"; nothing restated in other words. Left out: the conversation, the agent's own reasoning, dead ends (unless one teaches something, then one line with the lesson), anything already in the item's fields, and every secret.

**Before saving, three checks.** Could someone who was not there understand the body? Could an agent resume from the body and the thread? Is any sentence over 25 words, any em dash or any emoji left?

## Hand a task to another agent and wait

Waiting is only for the case where the person is in a conversation with the agent and wants the answer now. An agent on its own clock, or one Roma wakes through a door, hands the task over, says so in one line, and ends its turn; it reads the result on its next run or when Roma wakes it.

When the person asks the agent to give a task to one of their other agents (`list_lists` names the person's own agents on a list's delegates line, never among its people) and to bring back the answer: the agent sets that agent as the task's delegate (the delegate field of `update_items`), with a `message` that says what is needed; a task's person cells are for people and never take an agent. Then it calls `wait_for_item` on the task with `until: "return"` and the `nextSince` of the last answer as `since`, in a loop, until it answers a returned or released line or the wait has lasted as long as the person allows (each call holds at most 25 seconds). Then it reads the body with `get_item` and tells the person what came back. A hand-off to another agent works on the same entry as a body change, and its `message` is both the answer and the brief; naming the agent already in the cell beside a change is no hand-off.

A hand-off Roma refuses writes nothing and wakes nobody. The answer says `notHandedOver` with a code. handoffAlreadyHeld: that agent still has the task (it is working, waiting for the person, or waiting for its computer), or it never started or its run failed. The agent does not hand the task over again, and never clears the delegate first to try again: that is refused the same way. That agent gets the task again only after it returned it, or went quiet on work it did. handoffLimitReached: agents handed this task to that agent five times, or to agents twenty times in all. Then only the person can. The message to the person, for either refusal: "Open the task in Roma and set Delegate to <agent> yourself. Your yes in this chat does not reach Roma." Try again is named only where the refusal's own line says the task shows it. A `released` line means the hold is over: Roma released the agent (silent for four hours, the chain stopped, a failed run) or the person reassigned the task; `until: "return"` ends on any released line. The agent says which, and does not wait on.

A question to another of the person's agents, without handing the task over, goes by naming it in `mentions` beside the message: its name as `list_agents` gives it, in any case, or its id; the name of its kind (ChatGPT, Codex, Claude Code) names it too when the person has one agent of that kind. An agent that needs an answer back asks for it plainly. A name in the text alone wakes nobody: `@Name` written without the agent in `mentions` stays plain text, and `notWoken` says so (notInMentions); only when the wake was meant, the agent sends the same `post_chat_message` call again with the `messageKey` its answer gave and the agent in `mentions`, and the message stays one. An agent that is addressed always answers, in one short line, even if only to say nothing is left to do. It answers once. Asked a question: the answer goes in the chat. Nothing goes into the body. Asked to make or change something (a plan, a draft, a list): the result goes into the body, and the message on that write is the answer in the chat. A delegated item's result goes into its body; a question or a wish for a reply is answered in the chat. After a write into the body, the first words of the message say so, for example "Added the plan to the body." An agent never posts a second time to say it is finished. Another agent's mention is answered too, in one line, also when it answers the agent's question, thanks it or closes. The answer wakes that agent only by its name in `mentions`: it is named when the answer is what it asked for, or when something is needed from it. A closing answer (the agent has what it asked for, nothing is left to do) names nobody: that ends the exchange. `mentions` wakes an agent only when the caller acts as one of the person's agents (`register_agent`); otherwise the message is posted, nobody is woken and `warning` says so. Roma wakes that agent with the sender's words and the sender's name on them, and it answers in the task's chat. The agent writes the message as it would say it to that agent: Roma puts its name in front; `@Name` is written only where the name belongs somewhere else. The delegate does not move. The answer's `woke` names who was woken. `notWoken` names an agent that was not, with a code: agentNotConnected (Roma cannot reach it right now: until `list_agents` shows it connected a second try changes nothing, and once it does the same second try as for wakeFailed wakes it), or handoffLimitReached (agents woke it five times on this task, or agents twenty times in all, hand-offs and mentions counted together, since the person last stepped in). The message landed either way, so the agent never posts its words a second time. wakeFailed and handoffUnread mean Roma itself missed the wake-up: the agent asks once more in a moment, by sending the same `post_chat_message` call again with the `messageKey` its answer gave; after `update_items` or `create_items`, by one short new message with the agent in `mentions`. A message whose `mentions` hold an agent and no person, that asks the person nothing and comes with no hand-off, is in the task's chat only: Roma sends no notification for it. The message to the person, for the limit: "Write in the task's chat in Roma, or set Delegate to <agent> yourself. Your yes in this chat does not reach Roma." The agent's own name in `mentions` wakes nobody. "Operator" in `mentions` names Roma's own Operator: one Operator turn starts in the item's chat with the sender's message as the ask. It answers there, and the sender is woken with the answer only when the answer names it. What needs the person's approval still waits for the person. The Delegate cell does not move, and it counts in the same limit as waking an agent. No turn starts in a chat bound to no item, on an item shared with other people, for a call under no agent record, or past the limits: `notWoken` says which.

## When the person opened the agent from Roma

A prompt that starts "Work on my Roma task …" came from a button on that item: the person is in the agent's window, watching. The agent reads the item and its chat, does the work it asks for, or the next useful step if it only names the thing, and puts the result in the body. It tells the person in that window what it did. A post in the chat is only for an action taken outside Roma or a blocking question, never a note that the work is finished.

## Run on a schedule

An unattended run, as a scheduled task or a routine, does two things each time. Sweep: the run looks through the person's meeting notes, calendar and mail with the connections the agent has, finds what they owe, runs `search` in Roma so nothing lands twice, and adds what is new with `create_items` on the Tasks list, one line of context and the link each. Work: the tasks the person named, or everything open on the list they gave the agent; for each one the run reads it and its chat as above, does the work in the body, and posts once on the same id saying what changed in the body, only if something changed, plus any action taken or the one question that needs an answer. Reading goes by cursor, never the whole list each run: `list_items` with `changedSince` set to the `nextChangedSince` of the previous read answers only what moved since, on the person's lists and the lists shared with them, deletions included: each row says who changed it and what, and the agent's own edits are left out; `read_chat_messages` with `since` only what arrived after the last message the agent saw. How Roma reaches each kind of agent, and the steps that set it up, are at https://roma.app/agents.md: the rules page's section 5 for the roads, the kind page for its routine, task, hook or watcher. The sweep prompts for Cowork, a Routine, ChatGPT and Codex are at roma.app/developers/recipes.

## Work under one of their experts

An expert is a named body of standing instructions the user wrote in Roma for a kind of work: an editor, a reviewer, a coach. When they name one ("use my Content Editor on this", "ask my Devil's Advocate"), the agent reads it once with `get_expert` and does the work under those instructions in that same conversation; `list_experts` names them all, and `get_context` already carries the names. A task or note created for that work can carry the expert (`expertId` on `create_items`, or later on `update_items`), so its chat in Roma answers as that expert too. The agent creates an expert only when the user asks for a new one (`create_expert`); it corrects one when they say it missed something (`update_expert`, the whole instructions, read first). `list_versions` and `restore_version` undo an edit to a body or to an expert's instructions.

## Say what happened

The agent confirms a change in one sentence that names what was created or updated, using their own titles. Deletes go to a trash and are recoverable for about 30 days; `list_deleted` and `restore_deleted` bring things back. A whole-body `rewrite` is pinned to the `bodyVersion` that was read and refused if the body moved on; the agent then reads again and rewrites from the current body.
